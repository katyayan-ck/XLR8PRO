# Known Bugs Report

**This file is a continuously-updated, permanent bug tracker for this repository.** It is not
dated like `ai-changelogs-*`/`ai-findings-*` — it persists and gets edited in place. Every entry
stays forever, even once fixed, so there's a permanent record of what broke, when it was found,
and what fixed it (or what's still pending).

## Rule for every AI tool working on this repo

**Before starting work in an area, check whether it already has a known-bug entry here — don't
rediscover something already documented.** Whenever you find a new independent bug (not the
specific thing you were asked to fix, but something adjacent you noticed), add an entry
immediately, don't wait until the end of a task. Whenever you fix one, update its entry — don't
just note it in a changelog and leave this file stale. Whenever new information changes an
existing entry (root cause turns out different, severity changes, etc.), append to that entry's
Notes with a new "Modified" timestamp — never silently overwrite prior findings.

Entry format:

```
### BUG-XXX — <short title>

- **Status:** OPEN | FIXED | WON'T FIX (with reason)
- **Severity:** Critical | High | Medium | Low | Cosmetic
- **Found:** DD-MM-YYYY HH:MM — <how/where it was found>
- **Modified:** DD-MM-YYYY HH:MM — <what changed, if anything, since Found> (repeatable, one line per update)
- **Fixed:** DD-MM-YYYY HH:MM — <link to the ai-changelogs entry with the actual diff> (once fixed)
- **Where:** <file(s)/route(s)/screen(s) affected>
- **Description:** <what's actually wrong>
- **Proposed solution:** <what should be done, and any decision the fix depends on>
```

The result: `store()`/`update()`/`destroy()` all *look* like they succeed from an HTTP-status perspective (a normal `302`/`back()` redirect, same shape as a real success), while doing **nothing** — no row is ever created, updated, or deleted, and no `500` ever surfaces to reveal the problem, only a flash error message that a real browser user might not even notice among the page's own alert banners. Confirmed live for `destroy()`: `deleted_at` remained `NULL` in the database after a `302` "success" response. `store()`/`update()` were not separately reproduced with a full payload in this batch (destroy() was sufficient to prove the pattern, and `store()`/`update()` share the exact same `parent::{verb}Crud()` structure, so the same failure is a near-certainty, not just a suspicion), but this should be verified directly (not assumed) before considering the picture complete.
- **Fix applied (21-09-2026):** rather than patching the broken `parent::*Crud()` calls, `create()`/`store()`/`edit()`/`update()` were rewritten as fully custom methods against the REAL schema — `users` has no `code`/`name`/`person_id`/`employee_id` columns (which `setupCreateOperation()`/`setupUpdateOperation()`'s Backpack fields had assumed, compounding this bug with BUG-014's PRO-only `select2` fields), only `username`/`password`/`user_type`/`person_code`/`employee_code`/`is_active`. New hand-rolled Blade forms (`resources/views/admin/user/{create,edit}.blade.php`) replace Backpack's field system entirely — Create links an existing Employee (auto-filling `person_code`) or standalone Person, sets username/password/user_type/role/is_active; Edit additionally manages Employee org info (Designation/Branch/Location/Department/Division/Vertical/Segment/Sub Segment), requiring a change-reason/effective-date/remarks whenever any org field changes, which now correctly writes to `EmployeeHistory` (closing the prior open record, opening a new one) — see the "Users Listing + View pages" changelog entry and BUG-073/074 for what that required fixing first. `setupCreateOperation()`/`setupUpdateOperation()` gutted to just their permission checks, same reasoning as BUG-064/the `setupListOperation()` fix in the same batch — Backpack still dispatches these hooks automatically based on the route's `'operation'` tag regardless of which method actually handles the request. Verified live in rolled-back transactions: a real employee (`BMPL-0018`) successfully got a new login created via `store()`; `update()` correctly blocks an org-info change with no reason (redirects back with a validation error, employee row unchanged) and correctly applies + records history when a reason and effective date are given (exactly 1 new `EmployeeHistory` row, exactly 1 row left with `effective_to = null`).
- **Not fixed:** `destroy()` still calls `parent::deleteCrud()` (same broken pattern) — left alone since Delete wasn't part of the Users Listing + View request; the real-world "remove a user's access" need is now covered by the new Suspend/Revoke actions instead (see that changelog entry), which don't go through this broken code path at all.

  ```

  public function getDesignationCodeAttribute(): ?string
  {
      return $this->attributes['designation_code'] ?? $this->attributes['desig_code'] ?? null;

  public function getDesignationNameAttribute(): ?string
  {
      return $this->designation?->name ?? $this->designationLegacy?->name ?? null;

Every one of these three actions throws an uncaught 500-level `QueryException`. `store()`/`update()` are the two most fundamental actions in the entire Booking module — if this database's schema is what's actually running, no new booking can be created and no existing booking can be edited at all.

  - `update()` (now `BookingCoreService::update()`): sets `$booking->sale_type` (a `required`-validated field on the edit form, so it is *always* submitted and *always* differs from the always-null in-memory value) then `save()`s (an UPDATE) — reproduced live: `$b = Booking::find(1); $b->sale_type = '1'; $b->save();` throws `SQLSTATE[42S22]: Column not found: 1054 Unknown column 'sale_type'`.

- **Description:** `SHOW COLUMNS FROM xlr8_booking_master` (this session's `xlrm` local database) lists 50 columns. Missing from that list but read/written throughout `BookingCrudController`: `final_data`, `consultant`, `buyer_type`, `accessories`, `sale_type`, `branch_code`, `location_code`, `segment_code`, `model_code`, `variant_code`, `color_code`, `name`, `mobile`, `financier`, and others. Writing one of these fields via direct property assignment (which bypasses Eloquent's mass-assignment guard — confirmed via Laravel's `isGuardableColumn()`, which silently drops unknown-column keys only during `fill()`/`create()`/`update()`-the-array-method, not direct property sets) and then calling `->save()` builds a real `INSERT`/`UPDATE` statement against a column that doesn't exist, throwing `SQLSTATE[42S22]: Column not found`.
- **Scope now confirmed across all 9 Phase 4 services + Core CRUD:** the 8 non-OTF, non-Core services' `apply()`-style write methods were individually checked and only ever set real columns (confirmed via each service's own passing round-trip tests) — every one of those services' *read-side* `resolveEditData()`-equivalent methods mutate `$booking` with the same non-existent fields purely for that request's view rendering, and correctly never call `save()` afterward, which is why they were safe. `otfSave()`, `store()`, and `update()` are the only three Booking write paths in this controller that both set a non-existent field AND save — all three now confirmed broken, not just one.
- **Open question for the user/product owner, not guessed at here:** does this local `xlrm` database's schema reflect the actual production schema (in which case booking create/edit/OTF-save are live, critical, customer-facing bugs blocking the entire module), or is this local copy missing columns that a staging/production database already has (local-environment artifact, not yet a confirmed live bug)? This distinction changes the proposed solution significantly and needs a human decision — given the scope now includes the two most basic CRUD actions in the module, this is worth verifying urgently.
- **Proposed solution (pending the question above):** if confirmed live, add the missing columns via a proper Laravel migration, coordinated with whoever owns this table's schema outside Laravel's migration system (this table was not created by a Laravel migration in the first place — confirmed via `grep` finding zero migration files reference `final_data`, `sale_type`, or `branch_code`).
